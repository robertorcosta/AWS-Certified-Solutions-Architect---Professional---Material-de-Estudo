1.1 Estratégias de Conectividade de Rede

AWS Transit Gateway

Hub central para conectar múltiplas VPCs e redes on-premises. Substitui o modelo de peering mesh complexo.

  • Suporta: peering entre Regions, roteamento entre VPCs, integração com Direct Connect e VPN
  • Route Tables: permite segmentação de tráfego (ex: isolar VPCs de produção de desenvolvimento)
  • Multicast: suportado nativamente
  • Bandwidth: até 50 Gbps por attachment
  • Inter-Region Peering: tráfego criptografado entre TGWs de diferentes regiões
📝 Como cai na prova
  1. Empresa com dezenas de VPCs e conexões on-premises precisa de conectividade centralizada com roteamento transitivo, sem malha de peering. → Transit Gateway (hub-and-spoke) — VPC Peering não é transitivo e vira uma malha ingerenciável.
  2. Aplicação precisa de tráfego multicast entre instâncias em subnets diferentes. → Transit Gateway com multicast domain — peering e ENI não fazem multicast nativo.
  3. VPN híbrida de alta disponibilidade com balanceamento e reroute automático. → 2 VPNs de Customer Gateways distintos para um único TGW, com BGP + ECMP — rotas estáticas com failover de DNS são inferiores.
  4. Instâncias em duas Wavelength Zones diferentes precisam se comunicar diretamente com controle fino de roteamento. → conectar as subnets via Transit Gateway — Carrier Gateway é para saída à internet do carrier, não tráfego interno.
  5. Conectar milhares de contas/VPCs numa organização, reaproveitando o hub entre contas. → TGW compartilhado via RAM (Resource Access Manager) — evita um TGW por conta.

AWS Direct Connect

Conexão dedicada entre seu data center e a AWS. Reduz custos de rede, aumenta largura de banda e oferece latência mais consistente.

  • Tipos: Dedicated (1/10/100 Gbps) e Hosted (50 Mbps a 10 Gbps)
  • Virtual Interfaces:
    • Private VIF — acessa VPCs (via Direct Connect Gateway para múltiplas VPCs/Regions)
    • Public VIF — acessa serviços públicos da AWS
    • Transit VIF — conecta ao Transit Gateway
  • LAG (Link Aggregation Group): agrupa múltiplas conexões para aumentar throughput
  • Resiliência: para alta disponibilidade, use 2 conexões em locais diferentes + VPN como fallback
  • MACsec: criptografia na camada 2 (disponível em 10/100 Gbps dedicated)
📝 Como cai na prova
  1. Conectividade on-premises que precisa subir rápido, mas vai crescer para dezenas de Gbps. → VPN agora + pedido de Direct Connect em paralelo, migrando (cutover) quando o DX ficar pronto — o DX sozinho demora semanas; a VPN sozinha não escala além de ~10 Gbps.
  2. Banda dedicada e consistente com criptografia ponta a ponta. → DX (private VIF) + Site-to-Site VPN por cima do DX — o DX por si só não é criptografado.
  3. Um único DX precisa alcançar VPCs em várias Regiões/contas de forma privada. → Direct Connect Gateway associado a Transit Gateways/VGWs — evita um VIF por VPC.
  4. Alta disponibilidade da conexão física, sem ponto único de falha. → 2 DX em locations diferentes (ou LAG) + VPN de backup com BGP — uma única porta/conexão é SPOF.
  5. Tráfego do DX precisa de criptografia na camada 2 na porta física (compliance). → MACsec em conexões dedicadas suportadas — IPsec/VPN é camada 3 e não atende o requisito de L2.

AWS Site-to-Site VPN

Conexão criptografada (IPsec) entre rede on-premises e VPC via internet pública.

  • Virtual Private Gateway (VGW): endpoint do lado AWS para uma única VPC
  • Transit Gateway + VPN: permite VPN para múltiplas VPCs
  • Accelerated VPN: usa AWS Global Accelerator para melhorar performance
  • Throughput: ~1.25 Gbps por túnel (2 túneis por conexão VPN)
  • ECMP: Equal-Cost Multi-Path — com Transit Gateway, permite agregar múltiplas VPNs para mais throughput
📝 Como cai na prova
  1. VPN redundante que escala com o tráfego e faz failover automático, sem downtime. → 2 VPNs de Customer Gateways diferentes para um único Transit Gateway, com BGP e ECMP — roteamento estático com failover de DNS exige intervenção manual.
  2. Ao criar a VPN, quais dados o Customer Gateway exige. → ASN de BGP (se roteamento dinâmico) + IP público estático e roteável do dispositivo on-premises — o ASN só é exigido no roteamento dinâmico; o IP não pode ser dinâmico.
  3. Conectividade on-premises rápida enquanto o Direct Connect é provisionado. → VPN Site-to-Site imediata como ponte, migrando para o DX depois — a VPN sobe em minutos.
  4. Aproveitar a alta disponibilidade nativa de cada conexão VPN. → usar os dois túneis (cada um em endpoint AWS distinto) com BGP — toda conexão S2S já vem com 2 túneis em AZs diferentes.
  5. Reduzir latência/jitter da VPN para usuários globais. → Accelerated Site-to-Site VPN — usa a rede de edge do Global Accelerator; a VPN comum trafega pela internet pública.

DNS Híbrido (Route 53 Resolver)

Permite resolução de DNS bidirecional entre rede on-premises e VPCs.

  • Inbound Endpoint: permite que o DNS on-premises resolva nomes no Route 53 (on-prem → AWS)
  • Outbound Endpoint: permite que VPCs resolvam nomes no DNS on-premises (AWS → on-prem)
  • Resolver Rules: regras de encaminhamento condicional (ex: "*.corp.local" → DNS on-prem)
  • RAM Sharing: compartilhe regras entre contas via Resource Access Manager
📝 Como cai na prova
  1. On-premises precisa resolver registros de uma Private Hosted Zone na VPC (a consulta entra na AWS). → Resolver INBOUND endpoint, com os resolvers on-premises apontando para ele — inbound = on-prem → AWS; outbound é o sentido inverso.
  2. EC2 na VPC precisam resolver domínios de um DNS on-premises (a consulta sai da AWS). → OUTBOUND endpoint + forwarding rules indicando os domínios — a route table não configura forwarding de DNS.
  3. DNS altamente disponível e escalável (milhões de queries/s) sem ponto único de falha. → inbound e outbound endpoints em cada AZ + Resolver Rules por tipo de query — um endpoint único numa AZ é SPOF.
  4. Resolução DNS bidirecional entre on-premises e AWS na mesma arquitetura. → criar AMBOS os endpoints (inbound e outbound) — cada endpoint cobre só um sentido.
  5. Compartilhar as regras de forwarding do Resolver com muitas VPCs/contas. → Resolver rules compartilhadas via RAM — recriar as rules em cada VPC não escala.

1.2 Controles de Segurança

IAM Avançado e Cross-Account Access

Métodos de Acesso Cross-Account

  • IAM Roles (AssumeRole): método preferido. Conta A assume role na Conta B. Temporário e auditável.
  • Resource-based Policies: S3 bucket policy, KMS key policy, SQS policy — permite acesso direto sem assumir role.
  • AWS Organizations SCPs: limites máximos de permissão (guardrails) em nível de OU/conta.
  • Permission Boundaries: limite máximo para roles/users dentro de uma conta.

Ordem de Avaliação de Políticas

  1. SCP (Organization) — deny explícito prevalece
  2. Permission Boundary — limita o teto
  3. Identity-based Policy — o que o user/role pode fazer
  4. Resource-based Policy — o que o recurso permite
  5. Session Policy — restrição adicional em sessões assumidas
🔑 Conceito-chave para a prova Um deny explícito em QUALQUER nível sempre vence. Para cross-account, AMBOS os lados precisam permitir (exceto resource-based policies do S3 que podem conceder direto).
📝 Como cai na prova
  1. Auditor externo (com IAM user próprio) precisa de acesso somente-leitura em todas as contas, sem IdP. → IAM role read-only em cada conta + permitir que o user do auditor faça AssumeRole — roles dão credenciais temporárias; criar IAM user por conta é overhead.
  2. Devs (mas não Testers) da conta Dev precisam atualizar um bucket S3 na conta Production. → role na Prod confiando na Dev + na Dev permitir sts:AssumeRole ao grupo Developers (Deny aos Testers) — ExternalId é para terceiros, não cross-account interno.
  3. A conta Admin deve gerenciar recursos da conta Finance sem acessar os dados. → criar a cross-account role NA conta Finance (a dona dos recursos concede) — a role vive na conta cujos recursos serão acessados.
  4. Interpretar policy com Deny + NotPrincipal listando um usuário e o root. → só os listados têm acesso; todos os demais são negados — Deny + NotPrincipal nega todos EXCETO os listados.
  5. Delegar criação de roles a devs, forçando um permissions boundary que eles não possam remover. → Allow em iam:CreateRole com Condition iam:PermissionsBoundary + Deny em iam:DeleteRolePermissionsBoundary — só PutRolePermissionsBoundary não permite criar role.

AWS IAM Identity Center (SSO)

Gerenciamento centralizado de acesso a múltiplas contas AWS e aplicações de negócio. Substitui o antigo AWS Single Sign-On.

  • Integração: Active Directory (AD Connector ou AWS Managed AD), provedores SAML 2.0 externos (Okta, Azure AD), ou Identity Store built-in
  • Permission Sets: coleção de IAM Policies atribuída a users/groups para definir acesso AWS por conta
  • ABAC: Attribute-Based Access Control — define permissões uma vez, modifica acesso mudando atributos (cost center, title, locale)
  • Multi-Account: um login único para acessar qualquer conta da Organization
  • Application Assignments: SSO para apps SAML 2.0 (Salesforce, Box, Microsoft 365)
  • EC2 Windows: login único em instâncias Windows via SSO
📝 Como cai na prova
  1. Usar o Identity Center com um AD Microsoft self-managed on-premises, SEM cachear o diretório na AWS. → AD Connector como gateway, conectando o Identity Center ao AD self-managed — o Managed Microsoft AD cacheia e exige trust.
  2. IdP SAML 2.0 on-premises dando acesso federado ao console, sem criar IAM users. → autenticar no IdP → credenciais temporárias via STS → acesso pelo endpoint do Identity Center — AssumeRoleWithWebIdentity é só para IdP web/social.
  3. Acesso centralizado a múltiplas contas da Organization com conjuntos de permissão reutilizáveis. → Identity Center com permission sets atribuídos a grupos — viram roles nas contas-membro; IAM user por conta não escala.
  4. Permissões por atributo (departamento/projeto) vindas do IdP, sem policy por usuário. → ABAC no Identity Center usando atributos de sessão — ABAC escala por atributos; policies estáticas não.
  5. Federar usuários de IdP externo (Okta/Entra ID) para todas as contas com provisionamento automático. → Identity Center com IdP externo via SAML + SCIM — o SCIM sincroniza usuários/grupos automaticamente.
💡 SAML 2.0 Federation vs IAM Identity Center SAML 2.0 Federation é o "jeito antigo" — Identity Center é o recomendado. Se a questão menciona setup novo com AD, a resposta é IAM Identity Center. Se menciona sistema legado já com SAML configurado, pode ser SAML direto.

Criptografia e Gerenciamento de Chaves

AWS KMS (Key Management Service)

Sempre que ouvir "criptografia" para um serviço AWS, provavelmente envolve KMS. Keys são regionais.

Tipos de KMS Keys

TipoGerenciamentoRotaçãoVisibilidade
Customer Managed Key Você cria, gerencia, habilita/desabilita 90-2560 dias (default 365) + on-demand Total (policy + CloudTrail)
AWS Managed Key AWS gerencia (aws/s3, aws/ebs...) Obrigatória a cada 1 ano Pode ver policy e auditar
AWS Owned Key AWS usa internamente Varia Nenhuma (não pode ver/auditar)

Key Types

  • Symmetric (AES-256): uma chave para encrypt/decrypt. Usada por todos os serviços AWS integrados. Necessária para envelope encryption. Nunca exposta sem criptografia.
  • Asymmetric (RSA/ECC): par público/privado. Public key é downloadable. Use case: encrypt fora da AWS por quem não pode chamar a KMS API.

Key Material Origin

  • KMS (AWS_KMS): padrão, AWS gera e gerencia
  • External (EXTERNAL): BYOK — você importa. Responsável pela segurança fora da AWS. Sem rotação automática.
  • Custom Key Store (AWS_CLOUDHSM): material armazenado em cluster CloudHSM que você gerencia. Precisa de pelo menos 2 HSMs ativos.

Multi-Region Keys

  • Mesmo key ID, key material e rotação em todas as regiões
  • Encrypt em uma região, decrypt em outra (sem re-encrypt ou API cross-region)
  • NÃO são globais — são Primary + Replicas gerenciadas independentemente
  • Use cases: DR, DynamoDB Global Tables, Active-Active multi-region, distributed signing

Cross-Account KMS

Key Policy permite conta externa → Role na conta externa usa a chave. Ambos os lados precisam permitir.

AWS CloudHSM

  • Hardware dedicado (FIPS 140-2 Level 3)
  • Você gerencia as chaves (AWS não tem acesso)
  • Use quando: compliance requer HSM dedicado, SSL offloading, Oracle TDE
  • Integra com KMS via Custom Key Store

Envelope Encryption

Data Key criptografa os dados → CMK criptografa a Data Key. Padrão usado pelo SDK da AWS. Necessário para arquivos > 4KB.

📝 Como cai na prova
  1. Uma role na conta Production precisa usar uma CMK da conta Dev para decriptar num pipeline. → na key policy da CMK, permitir a conta Prod como key user com ações mínimas (Encrypt, Decrypt, GenerateDataKey*, DescribeKey) — use menor privilégio, nunca kms:*.
  2. O único principal da key policy foi deletado e o root não está na policy — a CMK ficou ingerenciável. → abrir chamado no AWS Support — sem o root na key policy, nem o root corrige; policy IAM não sobrepõe key policy.
  3. Permitir Encrypt/Decrypt apenas em chaves com uma tag específica (ABAC). → Allow com Condition StringEquals em aws:ResourceTag — kms:ResourceAliases é para alias, não tag.
  4. SSE-KMS em bucket com milhões de objetos gera custo alto de chamadas KMS. → S3 Bucket Keys — geram data keys locais, reduzindo chamadas por objeto.

Serviços-chave para DR

  • AWS Elastic Disaster Recovery (DRS): replicação contínua block-level de servidores para região de DR. Agent-based. Failover em minutos. Suporta failback.
  • S3 Cross-Region Replication: replica objetos automaticamente entre regiões
  • RDS Multi-AZ: failover automático para standby (síncrono, 30-60s)
  • RDS Cross-Region Read Replicas: replicação assíncrona para outra região (pode ser promovida)
  • Aurora Global Database: replicação < 1 segundo entre regiões, failover em < 1 minuto
  • DynamoDB Global Tables: multi-region, multi-active com replicação automática

DR Tips (do PDF do Stephane Maarek)

  • Backup: EBS Snapshots, RDS automated backups, S3 + Lifecycle + CRR, Storage Gateway, Snowball
  • HA: Route 53 failover, RDS Multi-AZ, ElastiCache Multi-AZ, EFS, S3. VPN como recovery do Direct Connect.
  • Replication: RDS Cross-Region, Aurora Global DB, DB replication on-prem → RDS, Storage Gateway
  • Automation: CloudFormation/Beanstalk para recriar ambientes, CloudWatch Alarms + recovery actions, Lambda automations
  • Chaos Engineering: AWS Fault Injection Simulator (FIS) — injeta falhas (CPU spike, terminate, network) em EC2, ECS, EKS, RDS. Usa templates pré-construídos.

AWS Backup

  • Gerenciamento centralizado de backups cross-service (EC2, EBS, S3, RDS, Aurora, DynamoDB, EFS, FSx, DocumentDB, Neptune, Storage Gateway)
  • Cross-region e cross-account backups
  • PITR (point-in-time recovery) para serviços suportados
  • Tag-based backup policies, scheduling (cron), retention, transition to cold storage
  • Backup Vault Lock (WORM): backups não podem ser deletados — nem pelo root user! Proteção contra ransomware.
📝 Como cai na prova
  1. DR de servidores EC2 entre Regiões usando Elastic Disaster Recovery (DRS) — melhor prática. → rodar drills periódicos lançando instâncias de teste e validando a recuperação — o DRS não provisiona recursos não-EC2 (use CloudFormation para o resto).
  2. Aurora Global Database com a Região primária fora do ar; o app conectava direto no cluster primário. → detach do cluster secundário (promove a gravável) e apontar o app para o novo writer — restore de snapshot ou adicionar Região nova não é failover.
  3. DR de RDS para outra Região com bom RTO/RPO, sem standby sempre ligado. → cross-Region automated backup replication e restaurar quando necessário — dá RTO/RPO em minutos sem custo de DB standby rodando.
  4. App multi-Região com Route 53 latency + weighted não faz failover ao derrubar uma Região. → anexar health checks aos records E ligar "Evaluate Target Health" — sem isso o Route 53 assume tudo saudável.
  5. Aplicação global ativo-ativo com leitura/escrita local de baixa latência em várias Regiões. → DynamoDB Global Tables — o Aurora Global tem uma única primária de escrita por vez.

1.4 Ambiente Multi-Account

AWS Organizations

Gerenciamento centralizado de múltiplas contas AWS em uma hierarquia de OUs (Organizational Units).

  • Management Account: conta raiz que cria a organização. NÃO use para workloads.
  • SCPs (Service Control Policies): guardrails que limitam o que contas/OUs PODEM fazer. Não concedem permissões, apenas restringem.
  • Consolidated Billing: uma fatura única, descontos por volume compartilhados
  • Delegated Admin: delega administração de serviços (Security Hub, GuardDuty) para conta membro

Estrutura Recomendada de OUs

  • Security OU: Log Archive + Security Tooling
  • Infrastructure OU: Networking, Shared Services
  • Workloads OU: Production, Staging, Development
  • Sandbox OU: contas de experimentação com restrições
📝 Como cai na prova
  1. Como adicionar contas a uma nova Organization. → criar contas novas dentro da Org OU, na management account, convidar contas existentes — não existe fluxo de "pedido de entrada" por conta-membro.
  2. Mover contas entre OUs pelo console falha por permissão — quais IAM perms. → organizations:DescribeOrganization + organizations:MoveAccount — DescribeAccount/AttachPolicy não são necessárias para mover.
  3. Mover contas de um OU para um novo OU. → no console de Organizations, selecionar as contas e Actions > Move — não é preciso remover/reconvidar nem passar pelo root.
  4. Exportar a lista de todas as contas-membro (IDs, e-mails, status). → console de Organizations (como IAM user) > Export account list (CSV) — evite o root para tarefas rotineiras.
  5. Admins da management account precisam gerenciar recursos nas contas Dev/Test (billing consolidado). → cross-account roles com as permissões NAS contas Dev/Test + AssumeRole — consolidated billing não concede acesso a recursos.

AWS Control Tower

Orquestra a criação e governança de um ambiente multi-account seguro (Landing Zone).

  • Landing Zone: ambiente pré-configurado com melhores práticas
  • Guardrails (Controls):
    • Preventive — SCPs que bloqueiam ações (ex: bloquear criação de access keys para root)
    • Detective — AWS Config Rules que detectam não-conformidade (ex: detectar se MFA do root está habilitado)
    • Proactive — CloudFormation hooks que validam antes do deploy
  • Guardrail Levels:
    • Mandatory: habilitados automaticamente (ex: bloquear leitura pública no Log Archive)
    • Strongly Recommended: best practices opcionais (ex: criptografia EBS)
    • Elective: comuns em enterprise (ex: bloquear delete sem MFA em S3)
  • Account Factory: vending machine para criar novas contas padronizadas usando AWS Service Catalog
  • Customizations for Control Tower (CfCT): aplica templates CloudFormation automaticamente em novas contas

Detect and Remediate Policy Violations

Fluxo: Control Tower detecta non-compliance → SNS → EventBridge → Lambda executa remediação automática

📝 Como cai na prova
  1. Padronizar rapidamente um ambiente multi-conta com contas de auditoria/log, baseline de segurança e governança. → AWS Control Tower (Landing Zone) — montar Organizations + SCPs + contas manualmente é lento e propenso a erro.
  2. Provisionar novas contas já em conformidade, de forma self-service. → Account Factory — aplica baseline e OUs automaticamente.
  3. Impor regras preventivas/detectivas de conformidade sem escrever cada SCP à mão. → Guardrails do Control Tower (preventivos via SCP, detectivos via Config) — são controles gerenciados prontos.
  4. Governar Regiões permitidas e detectar drift em todo o ambiente. → Region deny guardrail + detecção de drift na Landing Zone — o Control Tower monitora desvios da baseline centralmente.
  5. Empresa quer Landing Zone mas já tem uma Organization existente. → habilitar o Control Tower sobre a Org existente e inscrever (enroll) as contas — estende a governança sem recriar a Org.

3.4 Melhorar Confiabilidade

Eliminando Pontos Únicos de Falha

Checklist de Confiabilidade

  • ✅ Multi-AZ para todos os componentes stateful (RDS, ElastiCache, EFS)
  • ✅ Auto Scaling com health checks adequados (ELB ou custom)
  • ✅ Loose coupling via SQS/SNS (se um componente falha, não derruba outros)
  • ✅ Idempotência em processadores de mensagens
  • ✅ Circuit breaker pattern para chamadas externas
  • ✅ Dead Letter Queues (DLQ) para mensagens que falham repetidamente
  • ✅ Graceful degradation (funcionalidades não-críticas podem falhar isoladamente)

Self-Healing Patterns

  • ASG + Health Checks: instância unhealthy é terminada e substituída
  • ECS Service: task failure → scheduler lança nova task
  • Lambda: retry automático (async: 2 retries, sync: depende do caller)
  • RDS Multi-AZ: failover automático em ~30-60 segundos

Service Quotas

  • Monitore quotas com AWS Service Quotas + CloudWatch
  • Request increase proativamente antes de scaling events
  • Trusted Advisor alerta quando está perto do limite
📝 Como cai na prova
  1. O que acontece no RDS Multi-AZ quando a instância primária falha. → o CNAME é re-apontado para o standby — o IP não muda e não se cria uma instância nova.
  2. RDS ficou sem armazenamento; monitorar e crescer sem intervenção. → métrica FreeStorageSpace + Storage Autoscaling do RDS — FreeLocalStorage é métrica do Aurora (errada aqui).
  3. RTO de minutos / RPO de segundos custo-efetivo para falha de hardware EC2 sob ECS. → ECS capacity provider usando um Auto Scaling Group de EC2 — hot standby cross-region é caro; Fargate Spot sofre interrupções.
  4. Processo não-crítico sobrecarrega o EC2 do Beanstalk; melhorar a resposta com custo baixo. → Elastic Beanstalk Worker environment + SQS (desacoplar o processo) — trocar a instância não desacopla o culpado.
  5. MAC address fixo (licença) precisa sobreviver à troca de instância EC2. → Elastic Network Interface (ENI) destacada e reanexada — a ENI mantém MAC/IP ao mover para o standby.

  1. Reduzir o custo de NAT com muito tráfego para o S3, mantendo os patches externos. → Gateway Endpoint para S3 (mantendo o NAT para a internet) — o tráfego S3 deixa de ser cobrado pelo NAT.
  2. Achar serviços permitidos por SCP mas nunca acessados, para enxugar as listas. → IAM > Access reports > Organization activity — o CloudTrail é manual/90 dias e o Config não mostra isso.
  3. Ajustar o menor privilégio mantendo permissões usadas nos últimos meses. → Last Accessed Information via conta de gerência da Org — o Config mostra mudanças, não recursos acessados.
  4. Achar recursos ociosos como EBS/EIP não usados e instâncias subutilizadas. → Trusted Advisor (cost optimization checks) — o Compute Optimizer foca rightsizing de performance.
  5. Analisar a tendência de gasto por tag e detectar recursos que geram custo sem uso. → Cost Explorer + Cost Allocation Tags — o Budgets alerta mas não faz a análise detalhada.

EBS — Detalhes do Exame (do PDF)

  • Volume Types:
    • gp2/gp3 (SSD): uso geral, boot volumes. gp3: 3000 IOPS baseline, configurável até 16.000
    • io1/io2 Block Express: mission-critical, até 256.000 IOPS. Suporta Multi-Attach na mesma AZ.
    • st1 (HDD): throughput-intensive, frequentemente acessado (big data, log processing)
    • sc1 (HDD): lowest cost, infrequente (cold data, archive)
  • Snapshots: incrementais, armazenados no S3. FSR (Fast Snapshot Restore) para evitar latência de primeiro acesso.
  • Encryption: account-level setting por região para criptografar automaticamente novos volumes
  • Multi-Attach (io1/io2): mesmo volume em múltiplas EC2 na mesma AZ. Requer cluster-aware filesystem.
  • Data Lifecycle Manager: automatiza criação/retenção/deleção de snapshots por tags

Instance Store vs EBS

  • Instance Store: fisicamente no servidor, efêmero, milhões de IOPS, perdido no stop/terminate
  • EBS: network drive, persistente, até 256K IOPS (io2 Block Express), sobrevive reboot

EFS — Detalhes do Exame (do PDF)

  • Managed NFS, multi-AZ, Linux only (POSIX), pay-per-use, escala para petabytes
  • Performance Modes: General Purpose (default, latência) vs Max I/O (throughput, paralelo)
  • Throughput Modes: Bursting | Provisioned | Elastic (auto-scale, até 3 GiB/s reads)
  • Storage Classes: Standard → Infrequent Access → Archive (50% mais barato). Lifecycle policies.
  • One Zone: 90%+ economia, bom para dev. Compatível com IA.
  • Access Points: restringem acesso a diretórios específicos com POSIX user/group enforcement
  • Cross-Region Replication: RPO/RTO de minutos para DR
  • On-premises access: via Direct Connect ou VPN (mount por IPv4, não DNS)

FSx — Detalhes do Exame (do PDF)

  • FSx for Windows: SMB + NTFS + AD + DFS Namespaces. Multi-AZ. Backup daily para S3. Acessível via DX/VPN.
  • FSx for Lustre:
    • Scratch FS: temporário, sem replicação, burst 6x (short-term processing, cost optimized)
    • Persistent FS: replicado na mesma AZ, self-healing (long-term, sensitive data)
    • Data Lazy Loading: só carrega do S3 os dados que realmente processa (reduz custo e latência)
  • FSx for NetApp ONTAP: NFS + SMB + iSCSI, shrink/grow automático, snapshots, point-in-time cloning
  • Migrar Single-AZ → Multi-AZ: usar DataSync ou backup/restore
  • Reduzir volume size: criar novo FSx menor + DataSync para sync

Storage Gateway Types

  • S3 File Gateway: NFS/SMB → S3 (Standard, IA, One Zone-IA, Intelligent-Tiering). Cache local. AD integration para SMB.
  • FSx File Gateway: cache local de FSx for Windows (para branches com latência)
  • Volume Gateway: iSCSI → EBS snapshots. Cached (low latency recent data) vs Stored (full dataset on-prem, scheduled backups)
  • Tape Gateway: VTL via iSCSI para S3 + Glacier (substitui fitas físicas)

1. Redes e Conectividade Híbrida

Route 53 — Roteamento e Resolver

  • Failover sobre latency routing: só funciona se você anexar health checks HTTP/TCP aos records E ativar Evaluate Target Health no alias. Sem isso, o Route 53 assume tudo saudável e continua roteando para a região morta. Reduzir o weight da região com falha NÃO redireciona.
  • Distribuir leitura entre read replicas: use weighted records com peso igual, um por endpoint. ELB não aponta para réplica RDS.
  • Resolver INBOUND = on-prem resolve nomes na AWS (encaminha para o IP do endpoint). Resolver OUTBOUND + forwarding rules = AWS resolve nomes on-prem. Para milhões de QPS, endpoints inbound e outbound em cada AZ.

Direct Connect vs VPN

  • DX é lento de provisionar (semanas) e não é criptografado por padrão. Descarte-o quando o requisito for "rápido de implantar", "proteção fim-a-fim" ou migração urgente.
  • Conectividade rápida agora, DX depois: suba uma VPN e faça cutover para o DX quando ele ficar pronto.
  • DX HA: redundância vem de múltiplos DX locations distintos, não de AZs. Um private VIF serve a um único VPC (use DX Gateway para vários).
  • VPN HA sem intervenção: duas VPN connections de Customer Gateways distintos para um único Transit Gateway, com BGP + ECMP (reroute e balanceamento automáticos).

PrivateLink e VPC Endpoints

  • Interface Endpoint (PrivateLink): acesso privado a um serviço específico ou SaaS de terceiro — cria uma ENI com IP privado, sem internet/VPN/DX.
  • Gateway Endpoint: existe apenas para S3 e DynamoDB. Ótimo para alta banda a S3 (mais barato/seguro que NAT), mas mantenha o NAT se as instâncias ainda precisam baixar patches de fora.

Global Accelerator vs CloudFront

  • Global Accelerator: IPs anycast estáticos, caminho ótimo até a região saudável mais próxima e failover cross-region instantâneo. Escolha quando o gatilho é latência de rede + failover multi-região, sem cache.
  • CloudFront: CDN com cache no edge (estático + dinâmico/API); signed URLs para conteúdo restrito. Colocá-lo na frente derruba os logs da origem — habilite CloudFront access logs.
⚠️ Armadilhas de rede
  • Security Group não faz "deny". Para bloquear um IP/porta específico use NACL (deny em nível de subnet).
  • NAT Gateway é IPv4-only. Para saída IPv6 use egress-only Internet Gateway.
  • CIDR do VPC e DHCP option set são imutáveis (adicione CIDR secundário / crie novo option set). O VPC aceita até 4 CIDRs IPv4 secundários.
  • S3 Transfer Acceleration não funciona com Glacier.

2. Multi-Account, Governança e Config

Organizations e SCP

  • Deny explícito sempre vence e é herdado descendo a árvore. Permissão efetiva = interseção de SCP ∩ permissions boundary ∩ IAM policy.
  • Para bloquear ações perigosas de forma uniforme (ex.: cloudtrail:StopLogging, s3:DeleteBucket): prefira um Deny no root (exige All features).
  • Restringir região: um único SCP negando ec2:RunInstances exceto quando region = X (evite pares allow+deny conflitantes).
  • SCPs não concedem permissão — funcionam como guardrail máximo.

Refinar SCPs com dados reais

  • Para descobrir serviços permitidos mas nunca usados (e então restringi-los): IAM → Access reports → Organization activity (service last-accessed org-wide).
  • IAM Access Analyzer não faz isso — ele acha recursos compartilhados externamente. Access Advisor é por-entidade, não org-wide.

AWS Config (muito cobrado)

  • Conformance Packs: empacotam regras de compliance + ações de remediação como uma unidade, implantável org-wide (contas/regiões) com monitoramento contínuo.
  • Remediação automática: regras do Config disparam SSM Automation documents para corrigir recursos fora de conformidade.
  • É pré-requisito obrigatório do Firewall Manager em cada conta-membro.

RAM, Service Catalog e Budgets

  • RAM: compartilha recursos específicos (subnets, Transit Gateway, regras de Network Firewall/DNS Firewall e components/recipes/images do EC2 Image Builder) via resource share + principals. Não gerencia roles IAM.
  • Service Catalog Template Constraint: forma correta de restringir valores de parâmetro do CloudFormation (ex.: limitar o InstanceType permitido por time).
  • Budgets actions: ao cruzar o threshold, aplica SCP, IAM policy ou para EC2/RDS. Para impedir lançamento de instâncias acima do orçamento, use a ação que aplica SCP (parar EC2 só afeta o que já roda).

3. Identidade e Federação

Cognito — User Pool vs Identity Pool

  • User Pool = autenticação (diretório + federação com Google/Facebook/SAML). Identity Pool = autorização (entrega credenciais AWS temporárias).
  • Acesso guest/unauthenticated habilita-se no Identity Pool (identidade via GetId).
  • Permissões por papel: crie groups no User Pool e anexe uma IAM role a cada group — nunca policy direto no usuário.
  • User Pool authorizer é a melhor forma de autenticar muitos clientes num REST API no API Gateway.

STS e SAML

  • SAML → console/S3: o usuário autentica no IdP, recebe a assertion e chama AssumeRoleWithSAML no STS. O IdP não chama o STS pelo usuário.
  • AssumeRoleWithWebIdentity só para IdP público/social (OIDC). Para SSO corporativo SAML use SAML federation + IAM Identity Center.
  • Broker de identidade legado: autentica e chama GetFederationToken ou AssumeRole.

IAM roles e boundaries

  • EC2 acessa serviço AWS: sempre via IAM role anexada à instância — nunca access keys embutidas. A policy vai na role, não no recurso alvo.
  • Cross-account: a role é criada na conta dona dos recursos; a conta chamadora recebe permissão de AssumeRole. Consolidated billing sozinho não dá acesso.
  • Permissions boundary é teto: ação precisa estar na identity policy E no boundary. Para delegar criação de role forçando boundary, use iam:CreateRole com condition iam:PermissionsBoundary.
  • AD Connector = gateway ao AD on-prem sem cache (use quando "no caching" for requisito); Managed Microsoft AD faz cache.

4. Segurança e Criptografia

KMS

  • Cross-account: a key policy da chave dona autoriza o principal externo com ações mínimas (Encrypt, Decrypt, ReEncrypt*, GenerateDataKey*, DescribeKey) — nunca kms:*.
  • S3 Bucket Keys: forma mais barata de cortar custo quando milhões de objetos geram chamadas KMS por objeto.
  • Ler SecureString (SSM): basta kms:Decrypt (não Encrypt/GenerateDataKey).
  • Lockout: se a key policy não inclui o root nem outro admin e o único principal é removido, só o AWS Support recupera a chave. Deleção tem janela de 7–30 dias (default 30).

Detecção e postura (não confundir escopo)

  • Macie: descobre dados sensíveis em S3. Org-wide: Auto-enable ON + kms:Decrypt na service-linked role (sem isso, só reporta metadados).
  • GuardDuty: detecção de ameaças. Detective: investigação de findings (multi-account, por-região). Inspector: vulnerabilidades de EC2/software.
  • IAM Access Analyzer: acha recursos expostos a entidades externas.
  • Firewall Manager exige Organizations All features + admin account + Config em cada membro.

5. Bancos de Dados e Analytics

Aurora, RDS e DynamoDB

  • Aurora Global Database (DR): na falha da região primária, faça detach do secundário (promove a writable) e aponte o app para o novo writer. Restaurar snapshot NÃO é failover.
  • RDS Multi-AZ = standby síncrono, não legível, alvo de failover (re-aponta o CNAME). Multi-AZ DB cluster = standbys legíveis + failover: HA e read scaling na mesma região.
  • DynamoDB: query em atributo não-chave → GSI; picos de escrita → Auto Scaling; busca/filtro rico → replicar para OpenSearch (DAX e ElastiCache são cache, não busca).
  • Trocar instance class do RDS causa reboot mesmo sem Apply Immediately → aplique na janela de manutenção.

DMS, Redshift e Timestream

  • DMS faz replicação contínua (CDC); migração heterogênea usa SCT antes. Read replica não é DR para on-prem.
  • Redshift Spectrum consulta dados direto no S3, reduzindo o tamanho do cluster.
  • Timestream (série temporal serverless): memory store (writes rápidos) + magnetic store (analítico/retenção longa).

Analytics e Observabilidade

  • Log analytics open-source near-real-time: Kinesis Firehose → OpenSearch → Dashboards (VPC Flow Logs vão direto ao Firehose).
  • Athena Federated Query usa conectores Lambda para RDS/Redshift/on-prem; otimize com Glue, partition pruning e predicate pushdown.
  • CloudWatch Synthetics Canaries para heartbeat + GET/POST; dashboards podem exibir métricas cross-account e cross-region.
  • X-Ray para tracing distribuído com correlação automática.

6. Serverless, Integração e Containers

Lambda e API Gateway

  • Lambda timeout máx 15 min, mas o API Gateway corta em 29 s (não aumentável) → HTTP 504 mesmo com Lambda longa.
  • Tuning de memória: leia "max memory used" no CloudWatch Logs; subir memória também sobe vCPU.
  • Lambda Proxy integration com método ANY passa o request cru e evita re-deploy ao mudar a função.

Step Functions e Mensageria

  • Standard (até 1 ano, exactly-once) para tarefas não-idempotentes (pagamento). Express (≤5 min): Sync = at-most-once; Async = at-least-once (alto volume idempotente).
  • SQS FIFO garante ordem + dedup, mas não se converte de Standard (recrie). DLQ precisa ser do mesmo tipo do source.
  • KDS: retenção default 24h, até 7 dias (ou 365 long-term), com replay. Firehose entrega a S3/Redshift/OpenSearch.
  • Amazon MQ para lift-and-shift de broker JMS/AMQP/MQTT/WebSocket sem mudar código.

Containers e Compute

  • ECS Fargate = containers serverless. Prefira ECS a EKS quando não precisar da API Kubernetes.
  • App Runner: load balancing e scaling nativos (não adicione LB), CI/CD direto de GitHub/Bitbucket, VPC Connector para recursos privados. Mais simples que Fargate/EKS/Lambda para web apps.
  • ECS resiliente e barato: ASG de EC2 + ECS capacity provider (auto-substitui instância). Fargate Spot é interrompível → impróprio para crítico.
  • Elastic Beanstalk: update de plataforma via blue/green + swap de CNAME; worker environment + SQS desacopla jobs longos.

7. Migração, DR e Serviços de Edge

DR e Migração de Workload

  • AWS Elastic Disaster Recovery (DRS): DR barato com RPO em segundos / RTO em minutos via replicação block-level; use launch templates padrão e faça DR drills. AWS Backup não atinge esses valores.
  • AWS MGN: replicação contínua do workload completo + teste + cutover em janela de baixo tráfego; combine pilot light para críticos e bandwidth throttling sob restrição de rede.
  • Application Discovery Service: descoberta agentless, precisa de HTTPS outbound (443).

Snow, DataSync e Transfer

  • Snow Family para PB offline (limite de rede/compliance). Snowmobile só acima de 10 PB. Snowball Edge Compute Optimized quando precisa processar (ML) no edge antes de enviar.
  • DataSync migra NFS/SMB/HDFS online, mas não suporta SFTP como source → use Transfer Family para ingestão SFTP.

Edge: Wavelength, Local Zones, Outposts

  • Wavelength Zone: compute no edge da rede 5G do telco (latência mínima para devices 5G). Acesso à internet via Carrier Gateway (não NAT); inter-zona via Transit Gateway.
  • Local Zone: extensão da região num metrô (mais perto de usuários), não é edge-5G.
  • Outposts: serviços AWS on-premises. S3 on Outposts exige access points + VPC endpoint + conexão ativa com a Region.
✅ 7 Rs — leitura rápida Rehost (lift & shift, MGN, ideal para piloto) · Replatform (lift, tinker & shift — ex.: DB → RDS) · Refactor (decompor monólito em microservices) · Relocate (VMware/containers as-is) · Repurchase · Retain · Retire.

8. IA/ML Aplicada em Arquitetura

  • Rekognition consome direto de Kinesis Video Streams para face/objeto em tempo real (stream processor via CreateStreamProcessor, envio com PutMedia). Use RecognizeCelebrities para celebridades; DetectFaces é só imagem única. Rode a partir de Lambda para autoescala e custo.
  • Fronteiras de serviço (pegadinha frequente): Textract = texto de documentos · Transcribe = fala→texto (com custom vocabulary) · Polly = texto→fala · Translate = tradução · Comprehend = NLP (análise de linguagem natural).
  • Pipeline de mídia gerenciado: Step Functions + MediaConvert (arquivo) evita EC2 para transcode; MediaLive é para ao vivo; Elastic Transcoder é legado.

Novidades AWS 2025-2026 (Contexto)

Esta seção lista lançamentos recentes (re:Invent 2025 e 2026) que tocam temas cobrados e podem aparecer como opções em cenários. Trate como conhecimento de contexto, não como o centro da preparação. Recursos em preview raramente são a resposta correta na prova.

Networking e Content Delivery

Route 53 Global Resolver preview

Resolução DNS anycast segura e unificada para domínios públicos e privados globalmente, reduzindo overhead operacional em DNS híbrido.

Conecta com: Route 53 Resolver / DNS Híbrido. Em cenários de "DNS híbrido global com menor esforço operacional", é o candidato moderno.

AWS Interconnect — multicloud com Microsoft Azure preview

Conectividade gerenciada entre AWS e Azure. Relevante em cenários de arquitetura multicloud (antes resolvidos com Direct Connect + parceiros/VPN).

Segurança, Identidade e Compliance

AWS Security Hub (nova versão, GA)

Correlação de sinais de segurança em near real-time com priorização de risco. Evolução da visão consolidada de findings.

Cenário: "resposta mais rápida a riscos correlacionados entre o ambiente AWS".

Amazon GuardDuty Extended Threat Detection (EC2 e ECS)

Detecta ataques multi-stage com visibilidade unificada entre VMs e containers. Reforça o padrão "GuardDuty detecta ameaça → EventBridge → resposta automática".

Network Scanning no Security Hub

Descoberta de exposição de rede. Complementa Inspector e IAM Access Analyzer na identificação de superfície exposta.

Custos

Database Savings Plans

Novo modelo de compra que estende o conceito de Savings Plans para serviços de banco de dados, com flexibilidade de serviço/deployment.

Cenário: "reduzir custo de fleet de bancos com flexibilidade" — some ao mapa mental de Savings Plans (Compute/EC2) e RIs.

Serverless e Orquestração

AWS Lambda Durable Functions

Coordena múltiplos passos de forma confiável por períodos longos (segundos até 1 ano) sem pagar por tempo ocioso esperando eventos externos ou decisões humanas.

Compare com: Step Functions em workflows de longa duração — agora dá pra orquestrar dentro do próprio Lambda.

AWS Lambda Managed Instances

Roda funções Lambda sobre compute EC2 mantendo a simplicidade serverless — acesso a hardware especializado e modelos de preço de EC2, com a AWS gerenciando a infraestrutura.

IaC / Deploy

AWS CloudFormation Express mode

Confirmação de deploy em segundos para iteração mais rápida. Encaixa na seção de CloudFormation e estratégias de deploy.

Storage e Dados

S3 Tables, FSx ONTAP + S3, S3 Storage Lens, S3 Vectors
  • S3 Tables: agora com replicação cross-region/cross-account e Intelligent-Tiering (otimização automática de custo). Relevante para data lakes analíticos.
  • FSx for NetApp ONTAP integra com S3: acessa dados do file system via S3 para analytics/ML/IA sem mover ou copiar dados. Reforça FSx ONTAP como escolha multiprotocolo.
  • S3 Storage Lens: métricas de performance, suporte a bilhões de prefixos e export para S3 Tables.
  • Amazon S3 Vectors (GA): armazenamento e consulta de vetores em escala com custo bem menor que bancos vetoriais dedicados (cenários de busca semântica / RAG).

Compute / Database (menções rápidas)

Graviton5, EKS Capabilities, Aurora Serverless
  • Graviton5: melhor price-performance em EC2 — reforça o padrão "usar Graviton para reduzir custo/energia".
  • Amazon EKS Capabilities: orquestração de workloads gerenciada, reduz manutenção de infraestrutura K8s.
  • Aurora Serverless: ~30% melhor performance e scaling mais inteligente em mais regiões.
